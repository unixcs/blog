- 场景：在本地 `jp` NAS 上部署多个 free-api 项目，先逐个验证，再收敛为一个统一 API 入口。

## 用户目标
- 在本地 `jp` NAS 上部署多个国模免费 API 代理项目。
- 最终希望通过一个统一 API 地址调用这些模型能力。
- 本轮优先级：
  1. 内网使用
  2. 快速跑起来
  3. 先接入 `DeepSeek + GLM + Spark + Kimi`
  4. 先单个跑通，后续再统一
- 后续实际执行中，最终稳定方案聚焦在 `Kimi + GLM`，并已落地统一网关。

## 过程摘要
- 初始阶段先做规划，没有直接套用文章里的 `8000` 端口方案，而是决定采用独立端口逐个验证。
- 用户明确选择：内网使用、快速跑起来、优先接入 `DeepSeek + GLM + Spark + Kimi`、先单个跑通，后续再考虑统一。
- 在远端服务器上确认：Docker 与 Docker Compose 已安装，端口 `18001-18004` 空闲，可作为 4 个服务的宿主映射端口。
- 新建了工作区服务记录目录：
  `D:\Program\0\home\vps\jp\llm-free-api`
- 编写了服务记录文档：
  - `D:\Program\0\home\vps\jp\llm-free-api\AGENTS.md`
  - `D:\Program\0\home\vps\jp\llm-free-api\DEPLOYMENT.md`
- 在远端创建目录：`/opt/llm-free-api`
- 依次拉起 4 个服务容器：
  - `deepseek-free-api` -> `18001:8000`
  - `kimi-free-api` -> `18002:8000`
  - `glm-free-api` -> `18003:8000`
  - `spark-free-api` -> `18004:8000`
- 所有容器都成功在 `aarch64` 上启动，并且 `/ping` 健康检查返回 `pong`，说明镜像层面与 ARM64 兼容。
- 随后用户准备手动登录各站点获取 token，并在本地保存到：
  `C:\Users\fengx\Desktop\token.md`
- 读取 `token.md` 后确认：
  - 已有 `DeepSeek userToken`
  - 已有 `Kimi refresh_token`
  - 已有一版 `GLM chatglm_refresh_token`
  - `Spark` 决定不接入
- 开始真实联调：
  - `Kimi` 成功返回正常响应
  - `GLM` 第一次失败，日志显示 `refresh_token` 已过期
  - `DeepSeek` 失败，返回 `Invalid character in header content ["X-App-Version"]`
- 对 `DeepSeek` 做了进一步尝试：
  - 重建容器并注入环境变量 `DEEP_SEEK_CHAT_AUTHORIZATION`
  - 发现当前镜像即使已注入环境变量，接口层仍强制校验客户端 `headers.authorization`
  - 同时仍存在上游 `X-App-Version` 相关错误，因此当前版本不适合纳入可用方案
- 用户随后补充了新的 `GLM chatglm_refresh_token`
- 使用新 token 重新测试 `GLM`，成功返回正常响应，确认 `GLM` 成为第二个可用服务。
- 由此确定当前稳定组合为：`Kimi + GLM`
- 在此基础上，继续落地一个统一的本地 OpenAI 兼容网关，而不是引入现成重量级平台。
- 新建工作区目录：
  `D:\Program\0\home\vps\jp\llm-gateway`
- 自定义编写了一个轻量 Node.js 网关，不是第三方开源现成项目。
- 网关职责：
  - 提供 `GET /health`
  - 提供 `GET /v1/models`
  - 提供 `POST /v1/chat/completions`
  - 根据 `model` 路由到 `Kimi` 或 `GLM`
  - 服务端自动注入上游 token，客户端无需再传真实 provider token
- 网关文件：
  - `D:\Program\0\home\vps\jp\llm-gateway\app.js`
  - `D:\Program\0\home\vps\jp\llm-gateway\Dockerfile`
  - `D:\Program\0\home\vps\jp\llm-gateway\AGENTS.md`
  - `D:\Program\0\home\vps\jp\llm-gateway\DEPLOYMENT.md`
  - `D:\Program\0\home\vps\jp\llm-gateway\USAGE.md`
- 初始构建时使用 `node:22-alpine` 失败，错误为拉取元数据时描述符异常；随后切换为 `node:20-alpine` 成功构建。
- 将网关部署到远端目录：`/opt/llm-gateway/app`
- 构建并启动容器：`llm-gateway`
- 统一网关宿主端口：`19000`
- 使用现有 `Kimi + GLM` token 作为网关环境变量注入
- 验证统一入口成功：
  - `GET http://`局域网IP（已脱敏）`:19000/health`
  - `GET http://`局域网IP（已脱敏）`:19000/v1/models`
  - `POST http://`局域网IP（已脱敏）`:19000/v1/chat/completions`，`model=kimi`
  - `POST http://`局域网IP（已脱敏）`:19000/v1/chat/completions`，`model=glm-4-plus`
- 用户随后询问为什么模型列表里只有一个 `Kimi` 模型。
- 解释结论：当前统一网关中，`Kimi` 被有意只暴露为一个基础模型名 `kimi`；这不是 Kimi 只能有一个，而是当前网关模型映射策略的结果。`GLM` 则显式暴露了多个模型名：`glm-4-plus`、`glm-4-zero`、`glm-4-think`。
- 用户询问刚才使用的网关是什么。
- 说明结论：当前网关不是开源现成项目，而是根据当前场景自定义编写的最小 Node 网关。

## 关键结论
- `jp` 服务器上的 4 个 free-api 镜像都能在 `aarch64` 上启动。
- 当前稳定可用的 provider 组合是：
  - `Kimi`
  - `GLM`
- `DeepSeek` 当前镜像版本存在实现问题：
  - 注入环境变量后仍要求客户端传 `Authorization`
  - 上游还会报 `Invalid character in header content ["X-App-Version"]`
  - 不适合作为当前可用 provider
- `Spark` 本轮未接入，保持未使用状态。
- 统一入口已可用，地址为：
  - `http://`局域网IP（已脱敏）`:19000/v1/chat/completions`
  - `http://`局域网IP（已脱敏）`:19000/v1/models`
  - `http://`局域网IP（已脱敏）`:19000/health`
- 统一入口当前支持模型：
  - `kimi`
  - `glm-4-plus`
  - `glm-4-zero`
  - `glm-4-think`
- 客户端调用统一网关时，不再需要手动带 `Kimi` 或 `GLM` 的真实 token。
- `Kimi` 在模型列表里只有一个，是因为当前网关只注册了一个基础模型名 `kimi`，这是网关设计选择，不是平台限制。
