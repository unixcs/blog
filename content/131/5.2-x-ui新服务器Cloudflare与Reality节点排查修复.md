# x-ui新服务器Cloudflare与Reality节点排查修复

## 时间
2026-05-02

## 用户目标
- 在新服务器 ``你的服务器IP（已脱敏）`` 上继续处理 `x-ui`
- 保持当前 `Cloudflare Tunnel` 架构
- 优先复用现有证书、现有域名体系、现有 `x-ui` 配置
- 不破坏已经可用的面板、订阅和节点
- 所有修改前先备份数据库和关键配置
- 重点排查并修复：
  - `VLESS + WS + TLS` 节点在客户端无法连接的问题
  - `Reality` 节点分享链接和使用方式的问题
- 最终方向确认采用“双轨并存”：
  - `Cloudflare` 线路作为主力，隐藏源站 IP
  - `Reality` 线路作为备用，仅少量自用

## 背景与上下文
- 服务器：``你的服务器IP（已脱敏）``
- 面板入口：`https://xui.douy.indevs.in/WgjJiwoKMBuMFs/`
- 订阅入口：`https://sub.douy.indevs.in`
- 统一证书路径：
  - `/etc/ssl/douy-indevs-in/fullchain.cer`
  - `/etc/ssl/douy-indevs-in/private.key`
- Tunnel / Cloudflare 相关域名：
  - `xui.douy.indevs.in`
  - `sub.douy.indevs.in`
  - `vless.douy.indevs.in`
  - `vmess.douy.indevs.in`
  - `vmess20443.douy.indevs.in`
  - `vless9443.douy.indevs.in`
  - `vless11443.douy.indevs.in`
- 用户明确要求：直接执行，不只给方案；修改前先备份；不要破坏现有可用节点。

## 过程摘要
1. 首先对服务器做只读检查，确认 `x-ui`、`cloudflared`、证书文件、监听端口和面板/订阅入口状态。
2. 确认 `x-ui` 与 `cloudflared` 都在运行，证书有效，`xray` 监听 `443/8443/9443/11443` 等端口。
3. 发现外部访问 `xui.douy.indevs.in` 和 `sub.douy.indevs.in` 一度返回 Cloudflare 侧 `404`，随后继续核对本地服务、Tunnel 配置与数据库设置。
4. 读取 `/etc/cloudflared/config.yml`，确认各 hostname 到本地源站端口的映射，其中：
   - `xui.douy.indevs.in -> https://127.0.0.1:37937`
   - `sub.douy.indevs.in -> https://127.0.0.1:2096`
   - `vless9443.douy.indevs.in -> https://127.0.0.1:9443`
   - `vless11443.douy.indevs.in -> https://127.0.0.1:11443`
5. 检查 `x-ui` 数据库与 `xray` 运行配置，定位到 `9443`、`11443` 两条 `VLESS + WS + TLS` 节点的实际配置参数均存在且监听正常。
6. 对 `vless9443.douy.indevs.in` 的 WebSocket 握手进行了本机和公网双重验证，均得到 `101 Switching Protocols`，确认链路本身是通的。
7. 最终定位 `VLESS + WS + TLS` 节点问题的根因：`x-ui` 后台导出的分享链接把“后端源站端口 `9443/11443`”直接暴露给客户端，而在 `Cloudflare Tunnel` 架构下，客户端实际应该连接公网 `443`。
8. 随后利用 `3x-ui` 原生支持的 `externalProxy` 机制，修复 `9443` 与 `11443` 这两条入站的导出逻辑，使后台复制出来的链接能按 `域名 + 443` 导出。
9. 后续又排查了 `Reality` 节点。用户使用的分享链接是 `@xui.douy.indevs.in:443`，这会把面板域名当成 `Reality` 服务器地址，容易导致客户端连接失败或行为异常。
10. 对 `Reality` 节点进行修复：给 `443 Reality` 入站增加 `externalProxy`，将导出地址改为直连服务器公网 IP ``你的服务器IP（已脱敏）`:443`，保留原有 `Reality` 参数不变。
11. 在讨论架构后，用户确认采用“双轨并存”：主力用 `Cloudflare` 隐藏 IP，备用保留 `Reality` 直连节点，但不作为公开主力。

## 关键结论
1. `Cloudflare Tunnel` 架构下：
- 后端端口如 `9443`、`11443` 仅是服务器源站入站端口
- 客户端不应直接使用这些后端端口
- 客户端应连接各自域名的公网 `443`

2. `VLESS + WS + TLS` 节点本身并未损坏，问题主要是 `x-ui` 导出分享链接未适配 Tunnel 架构。

3. `3x-ui` 的 `externalProxy` 字段可以解决“后台监听端口”和“客户端对外端口”不一致的问题，是本次修复的关键机制。

4. `Reality` 节点不能像 `Cloudflare Tunnel` 一样隐藏源站 IP。`Reality` 本质上要求客户端直接连真实入口，因此不适合作为需要隐藏 IP 的公开主力节点。

5. 当前合理架构是：
- 主力：`VLESS + WS + TLS + Cloudflare Tunnel`
- 备用：`VLESS + Reality` 直连

## 执行动作
1. 只读巡检新服务器当前状态。
2. 核查 `cloudflared` 配置与 `x-ui` 数据库设置。
3. 确认 `9443`、`11443` 两条 `VLESS` 入站在 `xray` 中存在且监听。
4. 对 `vless9443.douy.indevs.in` 执行 WebSocket 升级测试，确认链路通畅。
5. 备份关键文件：
   - `/etc/x-ui/x-ui.db`
   - `/etc/cloudflared/config.yml`
6. 修改数据库中 `9443`、`11443` 两条入站的 `stream_settings.externalProxy`：
   - `vless9443.douy.indevs.in:443`
   - `vless11443.douy.indevs.in:443`
7. 重启 `x-ui` 并验证 `externalProxy` 已成功写入数据库。
8. 对 `Reality` 入站再次备份数据库。
9. 修改 `port=443` 这条 `Reality` 入站的 `externalProxy` 为 ``你的服务器IP（已脱敏）`:443`。
10. 再次重启 `x-ui` 并验证 `Reality` 的导出映射生效。
